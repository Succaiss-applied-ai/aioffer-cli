# 控件 Driver 分流与 Codex 修复策略

本文是控件自动化的强制开发策略。目标不是用一套通用操作覆盖所有招聘网站，而是先识别控件，再把它交给唯一、已登记、可验收的 Driver；批量测试发现新控件后继续扩充注册表。

## 1. 先分流，后执行

```text
实际投递 URL
  → ATS/站点路由
  → 字段语义 + 原生属性 + DOM/ARIA/交互签名
  → generic.native.v1
    | <site>.<control>.deterministic.vN
    | <site>.<control>.visual.vN
    | unresolved.custom.v1
```

URL 只确定有证据的 ATS/组件家族，不能单独证明某个控件应进入专用 Driver，更不能让某个公司接管整张表单。
公司例外必须同时命中精确 URL 家族、字段语义和控件签名；其余字段按真实原生/自定义结构进入共享类型 Driver。

一次控件执行只能进入一个 Driver。执行失败后不得改走键盘输入、DOM 强写、另一 Driver 或猜测坐标。

### 1.2 职位入口与表单控件分层

Application Entry Driver 负责从公开职位详情页进入登录页或申请表，不属于最终提交 Driver。
Application Page State Classifier 必须先对所有 HTTP(S) 招聘页执行，与站点 Driver 解耦。分类只产生
`job_detail`、`login`、`application_form`、`unknown`；初始加载和每次 URL/hash 或同页 DOM 状态变化后
都要求两次相同 URL + 页面状态指纹的稳定读数。只有稳定 `application_form` 能进入填写和提交；
`unknown` 超时必须失败关闭，不能降级为空表单。站点专用 Entry Driver 只有在分类器已确认
`job_detail` 后才能执行。

通用入口 Driver 只有同时满足以下条件才允许点击：

- 页面存在职位描述、岗位职责或任职要求等详情证据；
- 页面尚未检测到候选人申请表、登录表单或密码控件；
- 控件文案精确匹配“投递/申请/投递简历/立即申请/申请职位/Apply Now”等登记词；
- 当前观察中候选入口恰好为一个。

Driver 先扫描整个 DOM，再以有限步数滚动触发懒加载；点击后必须重新分类 URL、同页 DOM、登录页和申请表。
通用入口的唯一候选须在点击前再次确认同一 URL、可见性、启用状态和实时命中点后，才允许一次可信
指针；不得依赖后台标签页中的 DOM `.click()`。若真实页面证据证明同一 ATS 的两个控件是同一申请
入口的结构等价副本，可由站点专用 Entry Driver 精确登记“正好两个”的例外，并在指针发送前再次验签；
通用 Driver 仍不得接受重复入口。
多入口或点击后状态不变时返回 `application_entry_not_opened`。若后台隐藏页根本不创建节点，滚动
不是恢复手段。入口编排在首次页面观察前建立页面级焦点模拟，在同一后台标签内保持到点击后的
稳定分类完成，再撤销模拟并释放自己的调试连接；入口点击共享该连接，不能重复附加或提前撤销。
所有站点的新任务统一使用普通窗口内的后台标签，不再按 ATS 或公司创建独立窗口。
禁止修改 CSS 强行显示不存在的控件，也禁止把
公开页页头“登录”直接升级为通用登录墙。

Moka Entry Driver 登记两个结构模板，不按公司名扩展通用 Driver：既有 `BUTTON[type=button]`
的 `sd-Button-container-* button-container-*`，以及 `SPAN.button-*.apply-btn-header-*`。
SPAN 必须具有 pointer 光标、精确“申请职位”文案，并且同一 `job-details-*` 根中恰有一枚
`job-info-*` 直接子控件和一枚 `footer-*` 直接子控件；不能把任意两个同名 SPAN 当成等价入口。
新旧模板混用、多个主操作区、第三枚同签名入口或错误归属均停止。入口观察和可信点击前复核
共用 `openMokaApplicationFromDetailPage`，复核固定原 URL、登记类型和实时命中点，不保留第二套
选择器或旧控件对象。这里只打开公开岗位入口，不处理申请表的最终提交。

### 1.1 登记表是唯一分流来源

每个可执行 Driver 必须在 `extension/src/control-adapters/registry.ts` 中拥有一条可 JSON 序列化的结构化登记项。登记项至少包含：

- `registrationId`、`adapterCode`、Driver 类型和固定任务执行面；
- `site.code`、`site.name`、hostname/URL 家族模式；
- `field.category`、字段类别名称、`fieldNamePatterns` 和 `semanticKeyPatterns`；
- `control.type`、控件类型名称、DOM 类型、input 类型、readonly 要求和签名模式；
- 已登记动作允许的 `targetRoles`；
- 命中原因和验收证据摘要。

运行时不得只返回一个难以解释的 `adapterCode`。每次分流必须生成 `control-adapter-diagnostic.v1`，其中明确包含实际 `siteName`、`fieldName`、`controlType`、`adapterCode`、Driver、URL 家族、DOM 类型和命中原因。静态登记说明“允许什么进入 Driver”，运行时诊断说明“本次实际是什么”。

```json
{
  "schemaVersion": "control-adapter-diagnostic.v1",
  "registrationId": "moka.date-picker.deterministic.v2",
  "siteName": "Moka",
  "fieldName": "毕业时间",
  "controlType": "custom_date_picker",
  "adapterCode": "moka.date-picker.deterministic.v2",
  "driver": "site_deterministic"
}
```

注册表没有命中的控件也必须生成相同 Schema，`registrationId` 和 `adapterCode` 使用 `unresolved.custom.v1`，Driver 使用 `unsupported`。不得以空字符串、错误文案解析或前端猜测替代结构化字段。

### 1.3 公司控件例外与共享类型的确定性优先级

登记项显式声明 `routingScope`：`company_control` 高于 `shared_component`，后者高于 `native_control`。
同一层内，窄语义组件登记优先于字段语义为 `advisory` 的宽类型登记；语义仅用于进一步限定已匹配结构，
不能把文本框变成日历、把未知输入框变成下拉框。先计算所有候选并选出唯一最高优先级项，再执行；
同优先级多个候选返回 `ambiguous_control_registration`，不依赖数组顺序。诊断保留 `routingScope` 和
`matchedRegistrationIds`。失败后不切换 Driver，也不刷新、重新打开整表或改变执行面。

Moka 可编辑 `INPUT[text/search]` + `sd-Input-input`、`sd-Select-container`、`sd-Dropdown-container`
共同签名提供两个共享组件路由，适用于已验证的 Moka 申请页 URL 家族，而不是新增公司白名单：

- `moka.work-city.trusted-focus.v1`：工作城市选项；仅读取本控件拥有的弹层和城市叶子，不把省级分组标题当选项。
- `moka.flat-select.trusted-focus.v1`：平面下拉；必须确认单个本地菜单，只接受已取证的
  `Menu-content-item > option-label` 或直接文本 `Menu-content-item` 叶子，拒绝分组、树、日历和级联面板。
  匹配先做完整精确匹配；只有汉字/拉丁文双语两半允许唯一的本地化半边匹配，例如信息包
  `女/Female` 可唯一匹配页面 `女`。普通子串、中文业务斜杠选项和多个本地化候选不匹配；不得输入搜索、
  清空内部输入框、Enter 确认或借用其他字段的弹层。

电话国家/地区区号复用同一个平面下拉 Driver，但只有实时观察同时确认以下结构才获得默认选择权限：
同一个 `apply-field-*` 具有唯一电话标题，左侧是 `code-*` 内的 Moka Select/Dropdown 可编辑查询输入，
右侧是 `number-*` 内具有手机号语义的文本输入，且字段内恰好只有这两个可见输入。该标记不改变两者
原有稳定键、必填属性或答案归属。个人手机、紧急联系人电话、推荐人手机及其他人的电话，只要具有同一
区号/号码双控件结构就统一使用该区号策略；标题可包含对应人物语义。候选人本人手机号事实仍只能写入
候选人本人的右侧手机号框，不得流入紧急联系人或推荐人号码。没有区号 Select 的普通手机号文本框、
地址、邮编、普通数字下拉及缺少任一结构证据的控件均不获得此权限。

当前岗位对该精确稳定键的已确认区号答案优先，并按规范化后的完整区号精确比较；例如 `+86` 不等于
`+886`。没有确认答案时，一个真实叶子就选择该叶子；多个真实叶子时只选择唯一 `+86`。多个叶子没有
`+86` 或存在多个 `+86` 时，关闭本字段弹层、保持原展示值和查询值，并统一返回
`control_option_unavailable` 与当前选项，不猜第一项、不手输或清空区号。普通平面下拉继续拒绝覆盖已有
不同值。

区号回读以 `sd-Input-display-value-*` 的提交展示为准，弹层打开期间的 ghost 文本和内部查询值不是提交值。
成功还要求内部查询为空及弹层关闭；因此查询为 `1`、提交展示仍为 `+86` 时必须真实点击目标叶子，让网站
自己清除查询草稿，不能提前报成功。区号的局部校验只归属左侧 `code-*`；右侧手机号的空值或
“请输入正确手机号”不能被当成区号选择失败，也不能授权 Driver 改动右侧手机号。

共同流程是精确字段绑定、后台可信打开、唯一真实选项点击、必要时一次字段标题失焦、权威展示值和错误清除回读。
选项发现只打开/关闭一次而不选值；填写阶段另执行一次打开/选择/提交，不属于失败重试。
共享平面 Driver 每次重新观察后都核对原字段、原 URL、原 Driver；双语 Moka 标题按实际多语种 DOM 的主标题
稳定身份，不能因选中后 placeholder 消失而把城市错误归入工作经历。其他站点的斜杠标题及第三方关系字段不裁剪。

工作城市按用户指定的城市名称/前两个汉字包含匹配，但必须在当前真实叶子集合中唯一命中。
例如 `北京`、`北京市` 可以匹配 `北京市 / Beijing`；多个命中（包括相同文字的多个叶子）不能猜选。
英文使用完整输入，不截前两个字母。Driver 对已选择的完整叶子文案回读，外层事实回读复用城市规则。
该放宽不适用于籍贯省市区、日期、普通选项或任意文本；详见 [意向城市策略](PREFERRED_WORK_CITY_POLICY.md)。
真实页门禁见 [2026-09-03 分流验收](evidence/moka-control-type-routing-20260903.json)及
[2026-09-06 直接文本叶子验收](evidence/moka-flat-select-direct-item-20260906.json)。电话区号结构与基线事件
序列见 [2026-09-08 银河通用取证](evidence/moka-phone-calling-code-live-20260908.json)；该记录尚未执行本次
候选插件，也不是完整岗位提交验收。

## 2. 三类执行结果

| 分类 | 适用条件 | 执行方式 | 失败结果 |
|---|---|---|---|
| `generic_native` | 原生语义和标准回读可跨站点复用 | 通用原生 Driver | 阶段化执行错误 |
| `site_deterministic` | 依赖站点 DOM/事件序列，但可稳定确定性操作 | 站点专用确定性 Driver | 阶段化执行错误 |
| `unsupported` | 没有命中已登记 Driver，或证据不足 | 不执行 | `unsupported_required_control` |

### 2.1 站点校验驱动的自动提交

所有站点共用同一提交策略，不依赖某个租户的必填标记准确性：

- AI Offer 已解析的信息包是权威事实来源。正常上传保留；招聘网站在上传后自行解析不属于禁用范围。
  插件不主动选择、点击或确认“解析简历/覆盖/一键填充”动作，也不请求模型挑选这些动作。
- 初始填写只处理已有可信事实和当前岗位明确确认的可选答案；未知必填不猜测、不预先拦截。
  填写完成后直接提交，不运行第二次完整性或模型审计。精确目标和唯一 Driver 规则不变。
- 已精确绑定字段的空回读、非空回读不一致、站点提交状态未确认，只保留失败记录并暂缓该字段，
  继续其余字段后由网站校验接受与否，不反复填写，也不伪报 Driver 成功。
  身份语义污染、目标缺失/歧义、未登记控件等执行问题仍返回准确的控件诊断。
- 点击前保存字段错误基线。本次点击之后的新字段错误、局部错误重新断言或原生 invalid
  是本轮明确拒绝。新的可信提交后只保留两个窄例外：同一精确空控件仍持有字段内必填/缺失错误；或唯一允许的第二次提交后，第一次冻结稳定键中的字段内错误仍存在。
  冻结集外的旧错误、全局网络错误均不能通过例外。观察器不调用 checkValidity/reportValidity。
- 第一次提交明确拒绝后，冻结本次点击返回的稳定字段集合，不重新判断必填性。按页面顺序处理：有兼容信息包事实的字段只通过已登记
  Driver 定向复填一次并权威回读，无事实字段保持不动。若一个可复填字段都没有，直接返回第一次全部拒绝集，不执行无变化的第二次点击。
  只要至少一个有事实字段完成修复回读，才允许唯一一次再次提交。已有值覆盖权限仅属于冻结集合中的可复填精确稳定键。
- 第二次提交仍明确拒绝时，将第二次点击产生的全部报错字段统一交给用户补充或更正，包括非空值和
  已有信息包答案；不执行第三次提交。保留稳定字段标识、网站错误、实际下拉选项；选项发现失败单独
  记录，不能让其他字段的请求丢失。
- 单次定向复填不刷新/重开页面、不重传或解析简历、不重跑完整表单、不扩展字段、不调用模型造值，
  也不切换 Driver。任一精确字段执行或回读失败都停止再次提交并返回控件诊断。
- 页面真实标记为 `disabled` 的字段视为招聘网站托管值：初次规划、模型规划、必填阻塞检查及提交后定向复填均跳过，
  不比较信息包差异、不强行启用，也不向 Driver 下发写入。若网站提交后又明确拒绝该锁定字段，则返回
  `site_managed_disabled_field_rejected` 站点诊断，不误导用户补充一个无法编辑的字段。`readonly` 不属于此规则；
  Moka 的已登记下拉框和日历经常使用可操作的 readonly 输入。
- 用户确认后只续填原页的拒绝范围；旧红字不阻挡新的用户授权提交。实时城市选项只限制可选范围，
  不能仅因选项唯一就跳过候选事实/用户确认。成功、回执未知、登录/验证码等不能触发自动重提。
- 每次任务开始、用户补充续投、字段提交及网站拒绝后都重建稳定表单快照。快照签名包含字段身份/顺序、控件类型、当前值、选项、必填与校验状态；
  任一变化都使旧快照失效。因“是否实习”等选择新显示的条件字段，必须由下一次提交的新快照重新收集。
- 直接提交/最终确认后的 12 秒主动观察与 108 秒持久只读监控均可回传明确字段拒绝。等待释放执行槽，
  迟到拒绝通过 Gateway site_validation_rejected 转为补充信息；请求和答案最多 200 项。
  此变更需要插件和 Gateway 配套，不改变现有站点 Driver 的实际交互序列。

完整流程见 [SITE_VALIDATION_HANDOFF_POLICY.md](SITE_VALIDATION_HANDOFF_POLICY.md)。

#### 反例与事务边界

- 成功判定共用完整、可见的投递回执语句或已登记的回执 URL；“已收到验证码”“未投递成功”
  “提交成功后…”、上传成功、隐藏文本、按钮/导航文案不得命中。当前原生拒绝或登录/验证门不能
  被回执样式的文字覆盖。没有肯定证据时保持未知，不猜成功。
- 最终可信点击前先持久化提交意图；保存失败或任务已取消时不点击。点击后崩溃或网络不确定仅核验，
  不自动重提。只有确切字段拒绝或本次原生 invalid 才能清除检查点；全局网络错误不能清除。
- 普通提交按钮被 React 重绘不算第二次确认。普通“确定/确认”只用于明确的信息不一致投递弹窗；
  必填、登录、网络、验证码通知中的“确定”不是最终确认。第一次精确字段拒绝只授权上述单次定向修复；
  第二次精确字段拒绝统一交给用户补充/更正。
- 禁用按钮返回 `final_submit_disabled` 诊断，不强行启用，也不据此发明缺失字段。
- 缺失信息保留原标签与稳定字段集合；恢复不重新上传/解析简历，只续填原拒绝范围。原页丢失即停止，
  不新开重填。已知答案不在真实选项中的补充请求与其余未知答案汇总；选项发现失败保留结构化请求及单独诊断。
- 已知目标消失但没有明确条件解除证据时失败关闭，不能把“找不到控件”直接当作已修好。

#### 双语提交按钮识别

提交按钮使用 `extension/src/submission-action-policy.ts` 的单一短语库，观察器、首次提交定位、
二次确认定位及预览阶段判断共享同一份可序列化规则。完整中英文动作短语使用包含匹配，
不要求中英文逐字互译；短词“提交 / Submit”等只接受完整标签或完整双语组合。
匹配前归一全半角，允许换行/空白，但动作记录保留完整原文，供实时目标和本轮校验事件精确绑定。
取消、否定、说明、状态、草稿、上传、登录等文案优先排除；涉及同意/授权的复合提交保留独立授权门。

只有真实原生按钮、链接或显式 ARIA button 可成为提交动作，不能借父容器的文字提升其他按钮。
内层 span 归属同一物理按钮，两个独立同名按钮仍是两个候选。候选不可被动作展示上限隐藏。
观察和点击前都必须得到唯一可见启用目标；保存的 selector 不得绕过实时歧义检查。
该类修复属于共享只读识别/目标解析，执行仍由原有后台可信指针提交事务唯一负责，不新增公司 Driver、
不刷新重填、不抢前台、不放宽成功回执或网站拒绝交接。真实页只读证据见
[2026-09-03 双语提交验收](evidence/bilingual-submit-phrases-20260903.json)。

## 3. 通用 Driver 判定

只有同时满足以下条件才进入通用 Driver：

- 使用原生或跨站点已验证的 Web 语义；
- 不依赖站点 class、Portal 结构或私有事件序列；
- 标准事件可以更新站点真实状态；
- 可以通过 `value`、`checked`、`selectedOptions` 或标准 ARIA 状态权威回读；
- 至少有两个无关站点/夹具证明规则可复用。

通用 Driver 不得包含 `mokahr`、`beisen`、公司名称或站点专属选择器。

## 4. 站点专用 Driver 判定

出现以下任一情况，应建立站点专用 Driver：

- readonly 输入框驱动自定义弹层；
- 选项位于 Portal、虚拟列表、级联菜单、Canvas 或 Shadow DOM；
- 只有特定命中区或事件顺序可以打开控件；
- DOM value 会变化，但站点表单状态不会同步；
- 成功必须依赖站点错误提示消失、专用展示值或业务状态回读；
- 通用执行已经在真实页面失败，且失败可以由站点签名稳定复现。

专用 Driver 的 `detect` 必须校验有证据的 URL 家族和控件签名；公司例外还必须匹配该特定字段。
共享类型 Driver 的动作由结构决定，字段语义负责精确目标和信息包事实绑定。仅命中域名或字段名不能执行专用动作。

## 5. 自动 Driver 执行面契约

自动投递控件注册表只允许 `generic_native`、`site_deterministic` 和 `unsupported`。新任务执行面统一为
`background_tab`。页面类型和控件 Driver 与窗口选择分离，不再登记 `isolated_unfocused_window`。
`foreground_visual` 与 `focused_user_window` 仍被禁止。任何站点都不得通过 `tabs.update(active=true)`、
`windows.update(focused=true)`、`Page.bringToFront` 或等效动作抢占用户页面。

新任务显式选择普通、非无痕 Chrome 窗口并使用 `tabs.create({windowId, active:false})`；不能省略
`windowId` 后落入当前旧弹窗，也不能按相同 URL 接管用户或其他任务页面。没有普通窗口时准确报告，
不自动新建窗口或改用弹窗。独立的显式人工打开动作不受自动任务的后台策略约束。

显式人工打开岗位也使用同一普通窗口选择器，只把新标签设为 active；不得省略 windowId 而落入
遗留 popup。它不属于自动任务抢焦点，也不创建或恢复独立窗口。

续接只接受相同批次/岗位持久绑定的原标签；已跳转的飞书页面还要核对 origin、招聘 scope 和 job id。
升级前已暂停在旧弹窗的任务保留原文档，不迁移、不重开、不恢复窗口或抢焦点；这是旧会话兼容，
不是新任务开窗分流。关闭时只关闭该任务标签，不整窗关闭。协议明确可续接的验证码/身份核验、
缺失信息和回执等待继续保留原页并释放执行槽。记录实际 tabId、windowId、窗口类型与创建/续接来源。

页面焦点模拟只用于目标文档，不是激活浏览器标签。初始化、观察、点击、跳转失败均释放自己的连接；
附加失败不能断开他人的调试器。失败不切换窗口或执行第二个 Driver。

如果某个控件只能依赖聚焦用户窗口工作，它在自动投递中就是未支持控件，应返回
`unsupported_required_control`；不得把聚焦切换作为恢复、重试或兜底。显式人工辅助打开页面不属于
自动 Driver。

## 6. 未识别控件

无法证明通用或专用时返回 `unresolved.custom.v1`，不得操作页面。必填字段使用：

```text
unsupported_required_control: 暂不支持必填项「<字段名>」的<控件类型>；识别结果 <adapterCode>；<原因>
```

前端至少应显示字段名和控件类型；脱敏诊断同时保存 ATS、Driver 识别结果和失败阶段，供后续批量测试修复。

终态失败的 `details` 使用 `control-adapter-failure.v1`，顶层直接返回 `siteName`、`fieldName`、`controlType` 和 `adapterCode`，并在 `controlAdapter` 中携带完整 `control-adapter-diagnostic.v1`。前端不需要从中文错误字符串反向解析这些字段。

已登记 Driver 在打开、导航、选择或回读阶段失败时，应返回对应阶段错误，例如 `date_control_interaction_failed`，而不是改写成候选人缺少信息。

## 7. Codex 修复控件时必须完成的判断

| 证据 | 需要回答的问题 |
|---|---|
| URL/ATS 家族 | 控件属于哪个真实站点版本？ |
| 字段语义 | 这是日期、级联、文件、声明还是标准文本？ |
| DOM 类型 | 原生 input/select，还是 readonly/custom/portal/canvas？ |
| DOM/ARIA 签名 | 哪些稳定特征能区分该控件，哪些只是构建哈希？ |
| 可信事件 | 哪个真实鼠标/键盘序列会改变站点内部状态？ |
| 权威回读 | 如何证明 React/站点表单状态已更新？ |
| Driver 决策 | 通用、站点确定性、站点视觉还是未支持？ |
| 失败边界 | 识别、打开、导航、选择、回读分别如何报错？ |

Codex 必须把决策固化到注册表、代码和正负回归测试，不能只写在聊天、MR 描述或模型 Prompt 中。

## 8. 真实页面准入顺序

1. 在真实招聘页面复现原始失败并采集脱敏证据；
2. 在独立 worktree 或 Draft 分支实现原型；
3. 在同一个真实页面执行准备固化的同一分流、可信交互和回读序列；视觉 Driver 还必须覆盖截图、角色和坐标换算；
4. 回读目标值，并确认对应必填/校验错误消失；
5. 通过后才允许固化注册表、文档、发布元数据和可合并 MR。

单控件真实页面测试即可，不要求运行完整投递任务。夹具、单元测试、只打开弹层、获得焦点或只改变 DOM value 均不属于真实页面验收。控件测试不得点击预览或最终提交。

## 9. Moka 日期分流

此处“唯一弹层”指当前字段所属的独立日历容器，不是 CSS 选择器命中的原始 DOM 节点数量。Moka 的
`Dropdown-dropdown` 外层与 `panal-menu-wrapper` / `panel-menu-wrapper` 内层属于同一日历；观察时
沿用原先的外层可见容器，只归并具有祖先包含关系的包装节点，再解析内部年月日。两个独立并列弹层
仍失败关闭，不按顺序随意选择；其他字段的弹层不进入当前控件作用域。不得把正常嵌套结构误判为
“未打开”，再点击输入框关闭已展开的日历。

`moka.date-picker.trusted-pointer.v9` 先以 Moka URL、readonly `INPUT`、Dropdown 祖先和 `day_info` / `picker-addon` / 日期 placeholder 签名建立无需前台的 `site_deterministic` 候选。Moka 字段名由各企业自定义，因此通用路由中的字段名和稳定语义键只作诊断，不是准入条件；结构签名不足的普通 readonly 下拉仍保持未支持。表单规划期也保存当前控件及四层祖先类名，使自定义字段名不会在进入 Driver 前被错误归入普通键盘填写。

通用候选只允许先发送一次可逆的可信指针打开动作，再做第二阶段准入：控件作用域内必须只有一个可见弹层；日面板必须同时有唯一年/月标题、至少两个导航目标和不少于 20 个当前月日期叶子，月面板必须有唯一年份标题和至少 10 个不同月份，年份面板必须有合法年份范围、至少 8 个不同年份和导航目标。结构成立后才确认通用日期路由并允许导航/选择；否则按未支持控件停止。作业帮、tap4fun 等已由精确租户 URL、稳定字段归属和控件签名验收的窄路由可直接确认，不借用通用面板准入来推断字段含义或精度。

日期精度只读取控件自身证据或更窄租户登记：`type=month`、观察器的年月布局，或不包含“日/`DD`”的 `YYYY/MM`、`YYYY-MM`、中文年月 placeholder 才进入通用月精度；“开始时间”“结束时间”等字段标签本身不能降低精度。结构已证明是日历、信息包值却只有 `YYYY-MM`，但控件和租户登记都无法证明月精度时，指令仍从普通键盘路径隔离，通用 Driver 在任何点击前失败关闭。信息包中的 `YYYY-MM` 以 `{ year, month, day: 1 }` 传入日期 Driver；月面板 Driver 只消费年月，若租户控件以日网格提交隐藏内部值则只允许确定性的 1 日，产品回读和比较始终严格停留在 `YYYY-MM`。

执行顺序为：若前序 React 控件重建表单，先重新观察并按稳定字段身份绑定当前输入框 → 在后台焦点模拟面发送可信 CDP 指针打开 → 用 DOM 确认当前日历阶段 → 收集当前阶段后续动作需要的年份标题、月份标题、导航、目标年、目标月或目标日真实矩形 → 结合相同横坐标上的顶部 fixed/sticky 遮挡和视口边界计算剩余有符号位移 → 步长上限取视口高度 10% 并夹在 24–64px，最后一步只取剩余距离，由窗口及最近可滚动祖先消耗 → 重新观察全部目标；只有移动方向一致且剩余遮挡严格缩小时才继续下一步 → 全部目标通过 `elementFromPoint` 后执行当前唯一动作并再次回读阶段。日精度最终要求完整 `YYYY-MM-DD`，月精度要求 `YYYY-MM`；两者都要求弹层关闭和关联校验消失。

日历外壳超出视口不单独构成失败，只有当前阶段需要点击的目标必须可见且实时命中。渐进校正最多 12 步；目标集合无法容纳、页面不移动、实际移动方向相反、剩余遮挡不缩小、方向反复、达到上限、目标位于安全区但命中其他元素或状态不唯一时立即停止。整个序列不激活招聘页、不恢复标签页、不调用视觉模型，也不切换键盘、DOM 强写或其他 Driver。v8 的完整选日证据以及 v9 的作业帮年月路由和跨视口几何证据见 [CONTROL_ADAPTER_REAL_PAGE_EVIDENCE.md](CONTROL_ADAPTER_REAL_PAGE_EVIDENCE.md)。

作业帮租户 144908 的 `education.end_date.native`、readonly Moka Dropdown、`day_info` 与
`结束（YYYY/MM）` 同时命中时，先进入更窄的
`moka.zuoyebang.education-end-month.trusted-pointer.v1`。该登记只锁定已知字段并强制月精度，执行仍复用
通用 v9 的目标级几何、可信指针和回读状态机；URL、稳定键或控件签名任一不符就不进入此窄路由。

最终仍要求目标 `YYYY-MM`、弹层关闭和字段校验清除。此例外不适用于其他租户、其他活动、日精度、
空字段或结构不完整的面板。已加载 `0.15.92.2` 的真实控件验收见真实页面记录；没有据此宣称整表投递成功。

## 10. 已验证的 DeepSeek 地点分流

`moka.deepseek.location.trusted-pointer.v2` 只识别 DeepSeek 的 Moka 租户 URL、意向工作城市语义、可编辑文本 `INPUT`、Moka Select/Dropdown 祖先和地点签名，并路由到唯一的站点专用 Driver。Driver 必须使用单向状态机，把唯一一次滚动准备与打开后的只读观察分开，并返回一次性动作账本。

执行顺序为：用正式 selector 或地点字段语义重新定位唯一输入框 → 强制即时滚动、等待两个布局帧并重新绑定 → 用 `elementFromPoint` 确认实时命中点仍属于该输入框 → 在后台调试目标发送一次可信指针打开动作 → 只在当前可见弹层中查找精确匹配的 `option-label` 城市叶节点 → 排除同名省份标题 → 要求叶节点唯一 → 发送一次可信指针选择动作 → React 重建后按地点语义重新定位 → 城市已显示且弹层关闭但必填校验仍存在时，把同一视觉标题的嵌套 `DIV/SPAN` 包含链归并为一个语义目标 → 要求独立标题唯一并校验实时命中点 → 点击一次字段标题提交失焦 → 确认关联校验错误消失。

Driver 不使用输入搜索、键盘确认、DOM 强写、通用 Moka 下拉、刷新页面、整表重填、同控件重试或另一 Driver 兜底。失焦提交是首次选择的必要提交阶段，只在展示值已经匹配时执行一次。唯一弹层已打开且读取到真实城市叶子时，目标城市不存在返回 `leaf_missing + availableOptions`：必填项生成结构化补充请求，非必填项跳过。弹层打不开、目标歧义、事件、提交或回读失败才返回带 `driverStage` 的 `location_control_interaction_failed`。真实页面证据见 [CONTROL_ADAPTER_REAL_PAGE_EVIDENCE.md](CONTROL_ADAPTER_REAL_PAGE_EVIDENCE.md)。

## 13. 严格字段事实与 option-only 控件

字段规划和控件执行分别执行两道 fail-closed 门禁：

- 页面字段必须与信息包事实严格语义匹配；仅仅“值来自信息包”不构成匹配证据；
- 空的非必填字段默认不进入确定性预填或视觉模型输入，不产生页面写入，也不阻塞最终提交；简历推导、候选人信息包以及跨岗位复用资料均不能触发可选字段填写；
- 简历中的教育、工作、实习或项目条数不得触发招聘页“添加/新增”控件；重复区块默认保持站点原状，只有当前页面明确要求该区块时才允许准备最少条目；
- 只有用户已经为当前岗位的当前字段明确确认答案，或为当前岗位明确确认同语义岗位答案（如意向城市）时，该非必填字段才允许进入规划；页面已有的非必填值必须保持不变；
- 候选人本人的姓名、电话和邮箱不得映射到紧急联系人、外部推荐人、推荐人、内推人、介绍人、关系或其联系方式；只有字段稳定键、字段 ID 或规范化标签的精确补充事实可以填写；
- 下拉、combobox、autocomplete、cascader 和 custom select 只允许打开并点击页面实时存在的兼容选项；
- 禁止在选择类控件中输入搜索文本、发送 Enter、赋值或清空内部 input、触发文本字段回退；
- 实时选项不支持信息包值时保持字段不变。只有读取到可信选项集合时，必填字段生成带当前选项的结构化补充信息；无法建立选项证据才是控件错误。非必填字段跳过。

每次修复必须有负向测试证明“目标选项不存在时 input/change 事件为零且值未改变”，以及“未获当前岗位明确确认的可选字段不会接收简历、候选人信息包或跨岗位复用事实”。执行层必须重复校验该来源边界，不能只依赖模型提示词或规划阶段过滤。

## 14. Moka 招聘信息来源平面下拉

`moka.recruiting-source.trusted-focus.v1` 只识别 Moka 申请 URL、招聘信息来源/来源渠道语义、可编辑
`INPUT[type=text]`、Moka Select/Dropdown 祖先和真实平面选项签名，固定路由到后台站点确定性 Driver。

执行顺序为：按字段语义重新绑定唯一控件 → 启用后台焦点模拟但不激活标签 → 即时滚动并校验 Select
容器实时命中点 → 一次可信指针打开 → 读取唯一弹层的实时 `option-label` → 一次可信指针点击唯一精确
叶子 → React 重建后按语义重新绑定 → 同时回读展示值与弹层状态 → 若展示值正确但必填错误仍在，只对
同字段唯一非交互标题执行一次可信指针失焦提交 → 要求精确展示值、弹层关闭和字段校验清除同时成立。

Driver 不读取原生 `input.value` 作为选择成功证据，因为真实 Moka 控件提交后该值仍为空；也不通过
键盘、Enter、DOM value、合成 `.click()`、刷新、整表重填或另一 Driver 恢复。已有不同来源值时不覆盖；
目标选项不存在时保留实时选项并进入结构化补充信息；标题歧义或一次提交后校验不清除时失败关闭。

## 15. 通用协议确认 Driver

`generic.consent-confirmation.trusted-pointer.v1` 只接受页面观察器已标记为 `consent`、批次已授权
`allowConsentClick`、协议/隐私/授权/声明语义明确，并能绑定到唯一原生 `INPUT[type=checkbox]` 或标准
`role=checkbox` 的动作。它登记为 `generic_native`、`background_tab`；检测不得使用 ATS hostname、租户、
公司名称或站点 class。

执行顺序为：按已观察 selector、协议语义和最近单复选框容器绑定实时控件 → 唯一协议弹窗内的确认按钮
已启用时直接发送可信指针 → 若按钮不可用、不可见或直接确认未生效，则对弹窗滚动容器或跨域 iframe
可视区域发送可信滚轮到底 → 等待 10 秒让站点计时/解锁 → 重新定位并点击唯一确认按钮 → 要求弹窗关闭
且对应原生 `checked` 或标准 `aria-checked` 稳定为真。

`确认/确定/继续` 等通用文案只有在隐私、协议、授权或个人信息保护弹窗内才允许进入 Driver；
`预览并提交`、`确认提交`、`提交申请`、`立即投递` 等最终提交文案始终排除。多个匹配复选框、多个确认
按钮、滚动目标不可定位或最终回读失败均停止当前岗位，不切换 DOM `.click()`、值写入、键盘、刷新、
其他 Driver 或前台执行面。跨站点原生复选框和标准 ARIA 复选框夹具证明相同语义绑定与回读规则可复用；
真实页证据与最终提交隔离边界记录在 [CONTROL_ADAPTER_REAL_PAGE_EVIDENCE.md](CONTROL_ADAPTER_REAL_PAGE_EVIDENCE.md)。

零，不清除必填错误，也不通过岗位地点、简历地点或模型推断候选人的意向。

必须将其渲染为补充信息下拉框。用户选择后，Gateway 把答案作为 `user_confirmed` 事实写回原岗位并重新
排队；同一登记 Driver 才进入正式城市选择状态机。正式填写只点击用户确认且实时唯一的城市叶子；若
展示值已匹配但旧必填提示仍在，仅允许点击一次同字段唯一标题提交失焦。最终必须同时满足展示值精确
匹配、弹层关闭和局部校验清除。打开、选项归属、关闭、选择、提交或回读任一失败都不切换键盘、DOM
值写入、合成事件、刷新、重试或其他 Driver，也不得点击预览或最终提交。

## 19. 预览门与最终提交事务边界

页面最终动作的可见文案包含“预览”或 `preview` 时，允许观察后续确认步骤，但文案本身不能证明
网站没有提交副作用。因此首次指针前同样持久化防重意图，不声称已成功提交。执行器要求唯一可见启用
控件、点击前实时命中点和后台焦点模拟，并在目标
控件上临时记录可信 `mousedown`、`mouseup`、`click`。即使按下期间 React 重建控件且没有形成目标内
可信 `click`，也不得自动切换前台或再次点击预览。旧的无 click 前台重试例外已移除。

预览动作只有在观察到唯一最终确认控件、明确成功、提交后验证码等证据时才继续对应流程。
最终确认和“提交简历”等直接提交控件仍只允许一次可信指针，发送前必须落盘提交意图；之后只能核验
站点结果，不能重复点击。预览 click 后 12 秒仍没有明确回执/确认控件时返回结果未确认，保留防重
检查点；不得声称未提交、重试或转入没有最终确认依据的 `waiting_for_site_receipt`。整个路径
禁止 DOM `.click()`、键盘提交、`Page.bringToFront`、刷新、重填或切换 Driver。

提交事务的唯一执行归属仍是共享动作策略与可信指针执行器，不属于字段填写注册，也不得按公司新增
提交 Driver。预览、直接提交及确认控件的准备滚动、嵌套容器和视口校正显式使用 `instant`，避免
`auto` 继承站点 CSS 平滑滚动后在命中测试与指针发送之间移动目标；仍需实时唯一性与命中点复核。

主动核验已看到人工操作门时，先处理该状态，不再等待其背后的整表稳定。主动窗口截止后，必须通过
同一共享分类器重新读取当前验证码；新鲜且仍可见的验证码进入原有人工等待，即使来得太晚而未达到
常规连续三次观察阈值。已消失或陈旧证据不能产生人工等待。该截止读取不触发新提交；验证码由用户
在原页完成，持久监控只读确认结果。证据见
[2026-09-06 完整投递验收](evidence/submit-scroll-captcha-handoff-20260906.md)。

### 19.1 联系信息不一致的连续确认

手机号、邮箱等信息不一致提示继续归属同一共享提交执行器，不新增站点或字段 Driver。仅在当前
真实弹窗同时含“不一致”和“继续投递/提交”等既有语义、且没有验证码/必填/登录/网络等排除语义时，
才接受唯一可见启用的确认按钮。寻找所属上下文时可跳过无语义 dialog 角色的 footer/actions/buttons
包装，但必须停在最近的真实弹窗，不能跨语义 dialog 或借用兄弟弹窗的正文。观察定位和指针前的实时
定位必须同时满足这些规则，并再次匹配按钮文字与原提示身份。

普通最终确认仍限一次；信息不一致确认独立计数，每轮最多确认两个不同提示，同一提示即使重绘也不
重复点击。已发送确认后出现歧义只继续读取回执，不追加歧义点击或覆盖潜在成功。字段拒绝、验证码
交接、已持久化提交意图和原成功回执继续按原规则优先处理。提示身份仅用于本轮内存去重，不写入日志。

Moka 真实邮箱提示、自动确认及后续邮箱验证的记录见
[联系信息确认验收](../dev/moka-contact-confirmation/evidence/real-email-warning-qq.json)。
这是警告控件验收，不代表该轮已投递成功；手机号与其他顺序的实际覆盖范围见
[验收说明](../dev/moka-contact-confirmation/README.md)。

## 20. 控件级回读策略与选项来源

每条控件注册必须声明唯一 `readbackStrategy`，外层填写循环不得在专用 Driver 完成后再套用无关的通用
字符串比较。当前策略分为：原生值精确匹配、招聘页选项展示精确匹配、单城市行政区语义匹配、省市区
层级语义匹配、结构化日期/年月匹配和勾选状态匹配。未登记控件的策略固定为 `unsupported`。

行政区字段还必须区分值的来源：

- `job.requiredField.stable/field` 来自当前招聘页实时选项，保留省市区后缀，只折叠空白与展示分隔符后
  精确比较；
- `candidate.basic.nativePlace/currentCity` 与 `job.answers.preferredCity` 来自 AI Offer 的候选资料或自有
  地区分类，可以折叠“省/市/区/县/自治区”等行政后缀，但必须保持省、市、区各层语义一致；
- 省市区语义匹配不得扩大到招聘来源、学校、学历、普通下拉或文本字段，也不得把不同城市/区县判为
  相同；
- 专用 Driver 成功仍需新页面回读命中其登记策略。后续展示文本不能覆盖底层 Driver 的失败结果；
  空回读或提交未确认按第 2.1 节延后交给站点校验，真实执行失败保留原始阶段和错误码。

日期字段按控件精度校验，不按信息包字符串的展示形式校验：

| 控件类别 | 信息包示例 | 页面回读示例 | 判定 |
|---|---|---|---|
| 完整日期 / 日历日 | `2000-03-18` | `2000年3月18日`、`2000/03/18`、`2000-03-18T00:00` | 年、月、日全部相等 |
| 年月 / 月份区间端点 | `2025-09` 或完整日期 | `2025年9月`、`2025-09` | 只比较年、月 |
| 拆分年份控件 | 从日期拆出的 `2025` | `2025`、`2025年` | 年份数值相等 |
| 拆分月份控件 | 从日期拆出的 `9` | `09`、`9月` | 月份数值相等且范围为 1–12 |

精度只能由已登记 Driver、`FillInstruction.datePrecision` 或原生 `input[type=month]` 等控件签名决定；
不得因为最终回读缺少“日”就把日精度自动降为月精度。飞书经历月份端点固定为月精度，tap4fun 日历型
出生日期固定为日精度，后者即使收到旧的出生年月提示也不得忽略日期差异。无法解析的日期、非法日期、
错误月份或错误日期均失败关闭。日期值无论来自信息包还是招聘页答案，都只折叠显示格式，不改变其年月日
语义；这与招聘页下拉选项的来源精确匹配规则相互独立。

控件执行仍要求权威回读；仅因 AI Offer 行政区展示格式与站点展示格式不同，不得把已成功选择的字段
改写成“必填项缺失”。真实层级不同仍是错误内容；页面校验未清除或弹层未关闭时，Driver 不得报告成功。
编排层按第 2.1 节区分执行失败与读回未确认：延后验证不篡改 Driver 的失败结果，也不扩展交互序列。
未知必填项是否缺失由站点提交校验决定，不恢复全表提交前缺项预检。

## 21. Moka 籍贯后台执行面

`moka.native-place.cascader.trusted-pointer.v1` 保持原省市区定位、可信滚动、逐级选项和显式确认序列，
执行面改为已在 JXW 真实页验证的 `background_tab`。附加目标调试器后先启用页面焦点模拟，再执行
可信指针；不激活标签或窗口。`finally` 先撤销模拟焦点，再断开本次附加的调试器，附加失败不得
断开其他调试器。诊断记录活动标签前后 ID、实际点击/滚动数及零重试、零刷新、零整表重填。

已有正确完整值只回读，不重新打开或选择；已有不同值失败关闭。成功仍要求预期各级行政区一致、
弹层关闭和字段校验清除，外层新观察继续使用已登记的层级语义回读；后台支持不改变事实精度要求，
不把意向工作城市或其他自定义下拉纳入籍贯 Driver。

## 23. 原生文本日期与 label 内字段错误

## Workday 申请方式选择的追加候选

`workday.manual-application-entry.v1` 是申请入口，不是最终提交或简历解析。共享观察器只在 HTTPS Workday 岗位 `/apply` 根路径、唯一 main、Start Your Application 与岗位标题、三个完整同源同岗位方式链接同时成立时输出登记证据和 job_detail；它不把页眉 Sign In 当登录。原详情跳转后仅该登记方式可增加一次 Apply Manually 可信点击，点击前再次验证同一 URL、原目标与实时命中；不选择 Autofill with Resume / Use My Last Application，不循环、不接受未知方法页、不扩大通用入口唯一性。

方式选择后仍执行跨站点登录/表单分类。无可填写字段、唯一 main 中的 Sign In/Login 标题和明确提供方/邮箱登录按钮可构成登录门；显式 role=link 的返回链接不算登录按钮。已显示申请表、公开导航、隐藏标题或其他实际操作按钮都不由此推定登录。rc.5 已在滚动稳定的 BlackRock 原页验证完整方式选择到登录分类；新开详情页的前置 TalentBrew 滚动边界另行修正，不能由此宣称新建任务入口通过。

rc.6 已验证新建后台详情页首次入口的完整链路。TalentBrew advanced-job 双等价入口只取已重新确认的唯一顶端按钮，在即时滚动后读取当前位置并验证命中，再委托原共享指针一次点击。未改变一般入口的唯一性规则，也未改变其他站点的滚动或点击时序。后续 Workday 方式页只执行一次已登记手动申请，登录识别继续保持跨站点语义边界；证据见 rc.6 正式入口账本。
